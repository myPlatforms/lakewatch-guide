9단계 - AI 에이전트 사고와 탐지 규칙 만들기

사고 2에서는 아무도 비밀번호를 훔치지 않았습니다. 오염된 문서를 읽은 AI 에이전트가 자기의 정당한 권한으로 데이터를 내보냅니다. Alert 네 건을 세 로그 소스에 걸쳐 추적한 뒤, Create with Genie로 약한 Signal 세 개를 하나의 상관 탐지 규칙으로 묶습니다. 미션 M6과 M7입니다.

ℹ️

확인 범위
A와 B는 2026-11-23에 검증 워크스페이스에서 끝까지 수행했습니다. Create with Genie의 대화 내용은 실행할 때마다 달라지므로 한 번의 실행 예시로 읽으세요. 마지막의 보너스는 실행하지 않았습니다.

학습 목표

  1. 에이전트 세션을 게이트웨이, 도구 호출, 송신 로그에 걸쳐 추적한다
  2. 인젝션을 실은 문서를 찾는다
  3. Genie로 여러 테이블을 조인하는 상관 탐지 규칙의 초안을 만든다
  4. 규칙을 Query에서 시험한 뒤 저장하고, Alert가 생기는지 확인한다

A. 에이전트 사고 추적 (M6)

  1. Alerts에서 SD: Agent를 검색합니다. SD: AI gateway로도 검색합니다. Alert는 네 건입니다.

    규칙잡는 것
    sd_agent_gateway_prompt_injection게이트웨이 가드레일이 프롬프트 인젝션을 표시함
    sd_agent_restricted_data_access에이전트가 제한 등급 파일을 읽음
    sd_agent_egress_deny_burst샌드박스의 차단된 연결이 몰림
    sd_agent_egress_new_destination샌드박스가 처음 보는 도메인으로 데이터를 보냄

    검증 환경에서는 SD: Agent 검색에 에이전트 Alert 네 건과 함께 사고 1의 Alert 한 건도 나왔습니다. 제목 아래의 규칙 이름으로 구분하세요.

  2. "AI gateway flagged prompt injection" Alert를 열고 제목에 있는 세션 ID(session 뒤의 값)를 복사합니다.

  3. Query에 아래 타임라인 SQL을 붙여 넣고, 둘째 줄의 <session>에 세션 ID를 넣고, <catalog>를 본인 카탈로그로 바꿔 실행합니다.

    -- Paste the session ID from the alert on the next line
WITH s AS (SELECT '<session>' AS id),
w AS (
  SELECT min(time) AS t0, max(time) AS t1, any_value(sandbox_name) AS sandbox
  FROM <catalog>.signal_dynamics_lab.sd_ai_gateway_events, s WHERE session_id = s.id
)
SELECT time, 'AI gateway' AS source,
       IF(guardrails:input.flagged::boolean,
          'FLAGGED: ' || guardrails:input.categories[0]::string, 'model request') AS event,
       identity:requester::string AS detail
FROM <catalog>.signal_dynamics_lab.sd_ai_gateway_events, s WHERE session_id = s.id
UNION ALL
SELECT time, 'tool call', tool, target
FROM <catalog>.signal_dynamics_lab.sd_agent_tool_events, s WHERE session_id = s.id
UNION ALL
SELECT time, 'egress', action,
       coalesce(dst_endpoint:domain::string, dst_endpoint:ip::string)
         || ' · ' || round(traffic:bytes_out::bigint / 1e6, 1) || ' MB'
FROM <catalog>.signal_dynamics_lab.sd_agent_egress_events, w
WHERE sandbox_name = w.sandbox AND time BETWEEN w.t0 AND w.t1
ORDER BY time

  4. 결과를 시간순으로 읽습니다. 검증 환경에서는 41행이 나왔습니다.

테이블무엇을 보여 주나연결 키
sd_ai_gateway_events에이전트가 모델에 요청한 내용, 가드레일 판정session_id
sd_agent_tool_events에이전트가 호출한 도구와 읽은 대상session_id
sd_agent_egress_events샌드박스에서 나간 연결과 허용·차단 여부, 전송량sandbox_name

읽는 법

  • 흐름은 이렇습니다. 엔지니어가 공급업체 업데이트 요약을 요청 → 에이전트가 숨은 지시문이 든 공급업체 문서를 읽음 → 가드레일이 인젝션을 표시(차단은 하지 않음) → 제한 등급 공장 설계 파일 24건을 나열하고 읽음 → 송신 정책에 막힌 연결 6건 → 처음 보는 도메인으로 세 번에 걸쳐 약 45MB 업로드.
  • 타임라인은 전송량을 1,000,000바이트 단위로 보여 주고(16.1 + 13.4 + 15.8MB), Alert 제목은 1,048,576바이트 단위로 계산해 43.3MB라고 적습니다. 같은 전송입니다.
  • 가드레일은 동작했습니다. 다만 표시만 하고 차단하지는 않았습니다. 차단은 정상 업무까지 막을 수 있어 운영 환경에서는 표시만 하도록 두는 경우가 흔합니다. 그래서 탐지가 안전망이 됩니다.
  • 훔친 자격 증명이 없습니다. 에이전트의 원격 측정 로그(게이트웨이, 도구 호출, 송신)가 유일한 증거이고, 이 로그들이 다른 로그와 같은 곳에 있어야 추적할 수 있습니다.
  • 인젝션을 실은 문서는 게이트웨이가 표시한 요청 직전에 에이전트가 읽은 문서입니다.

확인 질문: 어느 문서가 인젝션을 실어 왔습니까?

정답

line3-servo-drive-update-v4.2.pdf입니다(검증 환경에서 확인). 타임라인에서 FLAGGED 행 바로 앞의 tool call 행을 보세요.

완료 기준: 오염된 문서 → 표시됐지만 차단되지 않음 → 제한 파일 읽기 → 차단된 시도 → 새 도메인으로 업로드의 흐름을 처음부터 끝까지 설명할 수 있습니다.

B. Genie로 탐지 규칙 만들기 (M7)

에이전트 Alert 하나하나는 약한 Signal입니다. 가드레일은 무해한 글에도 표시를 남기고, 에이전트는 원래 파일을 읽고, 샌드박스는 차단된 도메인에 닿기도 합니다. 그런데 한 샌드박스에서, 한 시간 창 안에, 이 순서로 일어나면 Critical 사고입니다.

  1. Detection rules에서 Create detection rule을 누릅니다. New scheduled detection rule 화면이 열립니다. 7단계에서 본 편집 화면과 같은 다섯 구역이고, 기본값은 Status: Active, Schedule: Every 1h, 심각도 Medium입니다.

  2. 오른쪽 위의 Create with Genie를 누릅니다. Genie 패널이 열리면서 "Help me create a detection rule"이 자동으로 전송되고, Genie가 무엇을 탐지할지와 어느 폴더에 둘지를 되묻습니다.

  3. 아래처럼 요청합니다. 폴더, 이름, 일정, 심각도, 제목 형식을 함께 적으면 되묻는 횟수가 줄어듭니다. <본인 이름>은 바꿔 넣습니다.

    Create a rule that fires when, in the same agent sandbox and window, the AI gateway flagged a prompt injection, then the agent read restricted files, then the sandbox sent more than 5 MB out. Use IN_TIMERANGE(time) for each table. Map to MITRE T1204.002 and T1567. Put it in the signal_dynamics_lab folder, name it sd_<본인 이름>_agent_injection_to_exfil, schedule every 1 hour, severity Critical. Start the signal summary with "SD:".
    항목값
    폴더signal_dynamics_lab (기본값은 detection)
    이름sd_<본인 이름>_agent_injection_to_exfil
    일정1시간
    심각도Critical
    MITRE ATT&CKT1204.002, T1567

  4. Genie가 계획을 세우고 테이블을 조사한 뒤 SQL을 시험하고, 검증을 통과하면 왼쪽 폼을 채웁니다. 검증 환경에서 계획은 여섯 단계였습니다. 원본 테이블과 컬럼 확인, MITRE 매핑, 탐지 SQL 작성과 시험, Signal 출력 구성, 일정·심각도·분류 설정, YAML 검증과 적용 순서입니다. Genie가 중간에 질문하면(예: 차단된 연결도 5MB에 넣을지) 답합니다.

  5. Genie가 쓴 SQL을 검토합니다. 확인할 것은 세 가지입니다.

    • 테이블마다 IN_TIMERANGE(time)이 있는가
    • 세 테이블을 sandbox_name으로 조인하는가
    • "표시 이후" 조건이 둘 다 있는가 (읽기가 표시 뒤, 송신이 표시 뒤)

  6. Signals 구역의 Signal summary가 SD:로 시작하는지 확인하고, 아니면 고칩니다. 검증 환경의 첫 초안은 "Agent prompt injection followed by …"로 시작해 SD: 검색에 잡히지 않는 제목이었습니다.

  7. Query에서 시험합니다. SQL을 복사해 붙여 넣고, IN_TIMERANGE(time)을 모두 time >= current_timestamp() - INTERVAL 1 HOUR로 바꾸고 테이블 이름을 전체 이름으로 씁니다. 재생한 지 1시간 안이라면 한 행이 나와야 합니다(검증 환경에서 아래 정답 SQL로 확인: 샌드박스 1개, 제한 파일 읽기 24건, 43.3MB).

  8. Detection input 구역의 Extend lookback에 2h를 넣습니다(이유는 아래 안내).

  9. Execution의 Status가 Active인 채로 Create rule을 누릅니다. 확인 창이 환경, 폴더, 규칙 이름은 만든 뒤에 바꿀 수 없다고 알려 줍니다. 다시 Create rule을 누릅니다.

  10. Alerts에서 새 Alert를 확인합니다. 검증 환경에서는 Extend lookback을 넣고 저장한 지 46초 뒤에 Critical Alert가 생겼습니다.

⚠️

저장했는데 Alert가 생기지 않을 때
규칙은 저장 직후 한 번 실행되지만, 그 실행이 보는 시간 창이 항상 "지난 1시간"은 아닙니다. 검증 환경에서 Extend lookback을 비운 채 만든 규칙은 저장 1분 안에 실행됐는데, 시간 창이 저장 34분 전부터여서 약 40분 전의 재생 이벤트를 놓쳤고 Alert가 생기지 않았습니다. 규칙을 편집해 Extend lookback에 2h를 넣고 저장하자 규칙이 다시 실행되어 Alert가 생겼습니다.

재생한 지 15분 넘게 지났다면 처음부터 Extend lookback을 넣고 저장하세요. 이미 저장했다면 Edit rule에서 값을 넣고 Save changes를 누릅니다. 다른 방법은 start_replay를 다시 실행하는 것입니다.

Extend lookback을 길게 두면 다음 정기 실행도 같은 이벤트를 다시 봅니다. 검증 환경에서는 35분 뒤의 정기 실행에서 같은 제목의 Alert가 하나 더 생겼습니다. 실습을 마치면 pause로 규칙을 끄세요.

ℹ️

Create with Genie는 시간이 걸립니다
검증 환경에서는 요청을 보낸 뒤 폼이 채워지기까지 약 15분이 걸렸습니다. 표본 조회 한 단계가 7분 동안 끝나지 않아 Stop으로 멈췄고(그동안 SQL 웨어하우스에는 실행 중인 쿼리가 없었습니다), 그 뒤 답이 두 번 "This response was interrupted before it finished."로 끊겨 Resend를 눌렀습니다. 세 번째에 SQL 시험과 폼 적용까지 끝났습니다. 실습 시간이 빠듯하면 아래 정답 SQL을 쓰세요.

⚠️

이름은 sd_로 시작하세요

pause와 teardown은 이름이 sd_로 시작하는 규칙만 찾습니다. 접두사를 빼면 실습을 정리해도 이 규칙이 켜진 채로 남습니다. 규칙을 삭제하면 그 규칙의 Alert도 함께 삭제됩니다.

막히면 아래 정답 SQL을 규칙 편집기에 붙여 넣습니다.

정답 SQL: 프롬프트 인젝션 → 제한 파일 읽기 → 유출
WITH flagged AS (
  SELECT sandbox_name, session_id, min(time) AS flagged_at,
         first(identity:requester::string, true) AS requester
  FROM sd_ai_gateway_events
  WHERE IN_TIMERANGE(time) AND guardrails:input.flagged::boolean = true
  GROUP BY sandbox_name, session_id
),
reads AS (
  SELECT sandbox_name, count(*) AS restricted_reads, max(time) AS last_read
  FROM sd_agent_tool_events
  WHERE IN_TIMERANGE(time) AND tool = 'files_read' AND sensitivity = 'restricted'
  GROUP BY sandbox_name
),
egress AS (
  SELECT sandbox_name, max(time) AS time,
         array_join(collect_set(dst_endpoint:domain::string), ', ') AS destinations,
         round(sum(cast(traffic:bytes_out AS BIGINT)) / 1048576, 1) AS mb_out
  FROM sd_agent_egress_events
  WHERE IN_TIMERANGE(time) AND action = 'Allowed'
    AND cast(traffic:bytes_out AS BIGINT) >= 5242880
  GROUP BY sandbox_name
)
SELECT e.time, f.sandbox_name, f.session_id, f.requester, f.flagged_at,
       r.restricted_reads, e.destinations, e.mb_out
FROM flagged f JOIN reads r USING (sandbox_name) JOIN egress e USING (sandbox_name)
WHERE r.last_read >= f.flagged_at AND e.time >= f.flagged_at

Alert 제목 템플릿:

SD: Agent session {session_id} for {requester}: prompt injection, then {restricted_reads} restricted reads, then {mb_out} MB to {destinations}

완료 기준: 직접 만든 규칙의 Alert가 Alerts에 나타납니다.

보너스: 신원 사각지대 찾기

사고 1에서 SSO로 AWS에 들어간 단계는 그 자체로는 Alert를 만들지 않았습니다. 일찍 끝냈다면 이 단계를 잡는 규칙을 만들어 봅니다. 이 보너스는 검증 환경에서 실행하지 않았습니다(Genie 스페이스가 만들어지고 start_replay가 링크를 출력하는 것까지만 확인).

  1. 위협 헌팅용 Genie 스페이스를 엽니다. 이름은 Signal Dynamics threat hunting (signal_dynamics_lab)이고, 노트북의 status가 링크를 출력합니다.

  2. 아래처럼 묻습니다.

    Did anyone federate into AWS with SAML from an IP that had failed Okta sign-ins in the same hour? Return user, IP, time and the SQL.

  3. 답으로 받은 SQL을 탐지 규칙으로 옮깁니다.

정답 SQL: 실패가 있던 IP에서의 SAML 로그인
WITH saml AS (
  SELECT time, sourceIPAddress AS source_ip,
         try_variant_get(userIdentity, '$.userName', 'string') AS federated_user,
         element_at(split(try_variant_get(requestParameters, '$.roleArn', 'string'), '/'), -1)
           AS role
  FROM sd_cloudtrail_events
  WHERE IN_TIMERANGE(time) AND eventName = 'AssumeRoleWithSAML' AND errorCode IS NULL
),
okta_failures AS (
  SELECT client:ipAddress::string AS source_ip, count(*) AS okta_failures,
         count(DISTINCT actor:alternateId::string) AS okta_users
  FROM sd_okta_events
  WHERE IN_TIMERANGE(time) AND outcome:result::string = 'FAILURE'
  GROUP BY ALL HAVING count(*) >= 5
)
SELECT s.time, s.source_ip, s.federated_user, s.role, o.okta_failures, o.okta_users
FROM saml s JOIN okta_failures o USING (source_ip)

Alert 제목 템플릿:

SD: {federated_user} federated into AWS as {role} from {source_ip}, which failed Okta sign-in {okta_failures} times
