5. 실습 환경 만들기

5단계 - 실습 환경 만들기

노트북 한 개로 실습 환경을 만듭니다. setup이 가상의 제조사 Signal Dynamics의 일주일치 합성 로그와 파서, 데이터소스, 탐지 규칙을 만들고, status가 준비 여부를 알려 줍니다. 실습 전날 미리 해 둘 수 있습니다.

ℹ️

확인 범위
2026-11-23에 검증 워크스페이스에서 폴더 등록과 setup을 실행해 결과를 확인했습니다. 노트북은 화면이 아니라 일회성 실행으로 돌렸으므로, 노트북 화면의 위젯 조작(B, D의 1–3)은 화면으로 확인하지 않았고 노트북 코드 기준입니다.

학습 목표

  1. 실습 시나리오의 두 사고를 설명한다
  2. 실습 노트북을 가져와 setup을 실행한다
  3. 실습 스키마를 Lakewatch 폴더로 등록한다
  4. status로 실습 환경이 준비됐는지 확인한다

A. 시나리오

Signal Dynamics는 컨베이어, 모션 컨트롤러와 이를 구동하는 PLC(Programmable Logic Controller, 산업용 제어기) 프로그램을 만드는 가상의 제조사입니다. IT는 AWS와 Okta SSO(Single Sign-On, 통합 로그인)로 운영하고, 가장 중요한 자산은 S3에 있는 공장 설계 파일입니다. 로그는 모두 합성 데이터이고, 공격자 IP는 문서용 IP 대역(RFC 5737)만 씁니다.

사고 1 · 신원에서 클라우드로 (Okta, CloudTrail)

비밀번호 스프레이 → 재사용 비밀번호 성공 → MFA(Multi-Factor Authentication, 다중 인증) 피로 공격 → SSO로 AWS 진입 → 탐색 → 백도어 IAM 사용자 생성 → 로깅 중지 → 공장 설계 파일 1,400건 다운로드 → 버킷 공개

여기에 미끼가 하나 섞여 있습니다. 정상적인 root 로그인으로, Alert를 무해 양성으로 닫는 연습에 씁니다.

사고 2 · AI 에이전트 (AI 게이트웨이, 도구 호출, 샌드박스 송신)

숨은 지시문이 든 공급업체 문서 → 게이트웨이가 프롬프트 인젝션을 표시만 하고 차단하지 않음 → 제한 등급 파일 24건 읽기 → 차단된 연결 6건 → 처음 보는 도메인으로 약 45MB 업로드

이 단계들을 하나로 묶는 규칙은 없습니다. 9단계에서 직접 만듭니다.

피해자, IP, 도메인은 사고를 재생할 때마다 무작위로 정해집니다. 단계별 MITRE ATT&CK 기법과 각 단계를 잡는 규칙은 10단계의 참조 표에 있습니다.

B. 노트북 가져오기

  1. Databricks 담당 어카운트팀에서 받은 signal_dynamics_lab.py 파일을 준비합니다. 이 사이트에서는 내려받을 수 없습니다.
  2. 워크스페이스에서 Workspace → 본인 홈 폴더 → ⋮ → Import → File을 선택하고 그 파일을 올립니다.
  3. 가져온 signal_dynamics_lab 노트북을 엽니다.

노트북은 워크스페이스 어디에 두어도 됩니다. 다만 사고를 재생하면 이 노트북 경로로 자동 일시 중지 Job이 예약되므로, 실습이 끝날 때까지 노트북을 옮기거나 지우지 마세요.

위젯

노트북을 한 번 실행하면 위쪽에 위젯이 나타납니다.

위젯기본값내용
actionstatussetup, status, start_replay, pause, teardown 중 하나
catalog(비어 있음)비워 두면 Lakewatch 환경을 자동으로 찾습니다. 아래 "카탈로그 선택" 참고
schemasignal_dynamics_lab실습 리소스를 만들 스키마
warehouse_id(비어 있음)비워 두면 이름에 starter가 들어간 웨어하우스, 없으면 서버리스 웨어하우스를 고릅니다
autopause_hours3사고 재생 뒤 자동 일시 중지까지의 시간
confirm(비어 있음)teardown할 때만 스키마 이름을 입력

카탈로그 선택

catalog를 비워 두면 노트북은 __lakewatch 스키마가 있는 카탈로그, 즉 Lakewatch 환경을 찾습니다.

상황결과
환경이 없음"Lakewatch isn't enabled in this workspace yet" 오류. 2·3단계를 먼저 하세요
환경이 하나그 카탈로그를 씁니다
환경이 여럿이고 lakewatch가 있음lakewatch를 씁니다
환경이 여럿이고 lakewatch가 없음오류. catalog 위젯에 카탈로그 이름을 입력하세요

노트북은 실행할 때마다 선택한 카탈로그를 출력합니다("Your Lakewatch Environment: …"). 이 가이드의 <catalog> 자리에는 모두 이 이름을 씁니다.

C. 실습 스키마를 폴더로 등록

Lakewatch는 폴더로 등록된 스키마에만 파서, 데이터소스, 탐지 규칙을 만들 수 있습니다. 실습 노트북은 signal_dynamics_lab 스키마를 SQL로 만들 뿐 폴더로 등록하지는 않으므로, setup 전에 직접 등록해야 합니다. 이 작업에는 카탈로그의 MANAGE가 필요합니다(새 스키마를 만들 때는 CREATE SCHEMA도).

⚠️

등록하지 않으면 setup이 실패합니다
검증 환경(2026-11-23)에서 등록 없이 setup을 실행하자 파서를 만드는 단계에서 아래 오류로 멈췄습니다. 그때까지 스키마, 볼륨, 합성 로그는 만들어져 있었습니다.

BadRequest: schema 'signal_dynamics_lab' is not a registered folder in environment '<catalog>'

  1. Lakewatch에서 Settings → Environment → Folders의 Add folder를 누릅니다.

  2. Schema에서 하나를 고릅니다.

    선택언제입력
    Create a new schemasetup을 아직 실행하지 않았을 때Folder name에 signal_dynamics_lab
    Use an existing schema스키마가 이미 있을 때 (예: 위 오류로 setup이 멈춘 뒤)Folder schema에서 signal_dynamics_lab 선택

  3. 권한을 정합니다. 새 폴더에는 All account users가 Folder admin으로 들어 있습니다. 모든 사용자가 이 폴더를 관리할 필요가 없으면 Add principal로 진행자(와 참가자 그룹)를 추가한 뒤 All account users를 Remove합니다.

  4. Save를 누릅니다.

검증 환경에서는 오류가 난 뒤 Use an existing schema로 등록했습니다. Create a new schema로 먼저 만드는 순서는 문서 기준이며 직접 해 보지는 않았습니다. Use an existing schema 목록에는 접근할 수 있고 아직 폴더가 아닌 스키마만 나옵니다.

기본 폴더 두 개와 달리 추가한 폴더에서는 권한 그룹 다섯 개(Folder admin, Datasource manager, Detection rule manager, Alert triage, Custom)를 모두 고를 수 있습니다. 참가자가 미션을 수행하려면 이 폴더의 Detection rule manager와 Alert triage가 필요합니다.

완료 기준: Folders 목록에 signal_dynamics_lab이 보입니다.

D. setup 실행

  1. 노트북에 Serverless 컴퓨팅을 연결합니다.
  2. action을 setup으로 바꿉니다.
  3. Run all을 누릅니다. 약 2분 걸립니다.

setup이 만드는 것은 다음과 같습니다(노트북 코드 기준).

종류내용
스키마·볼륨<catalog>.signal_dynamics_lab, 볼륨 sd_raw_logs
테이블sd_threat_intel_ip(위협 인텔리전스 IP 목록), sd_lab_replays(재생 기록)
합성 로그24시간 전에 끝나는 일주일치 Okta, CloudTrail, AI 에이전트 로그. 볼륨에 이미 로그가 있으면 다시 만들지 않습니다
파서사용자 지정 파서 4개(sd_okta_system_log, sd_agent_egress_ocsf, sd_ai_gateway, sd_agent_tools). CloudTrail은 내장 aws_cloudtrail 파서를 씁니다
데이터소스5개(sd_okta, sd_cloudtrail 등). 일정은 10일 간격, 컴퓨팅은 성능 최적화. 평소에는 돌지 않고 필요할 때 노트북이 수집을 직접 실행합니다
탐지 규칙17개(신원·클라우드 13개, AI 에이전트 4개). 꺼진 상태로 만들어집니다
대시보드AI/BI 대시보드. 노트북과 같은 폴더의 Signal Dynamics dashboards (signal_dynamics_lab)에 만들어집니다. setup은 2개(Security telemetry overview, Identity & cloud risk)만 만들고, 세 번째(Detection & alert activity)는 __lakewatch.signals가 생긴 뒤 start_replay가 추가합니다

마지막에 일주일치 로그의 수집을 시작합니다. 수집에는 약 10분이 걸립니다.

검증 환경에서 setup이 출력한 내용의 일부입니다.

ok       schema, Volume sd_raw_logs, sd_threat_intel_ip, sd_lab_replays
created  parser sd_okta_system_log
created  datasource sd_okta -> sd_okta_events
created  rule sd_okta_password_spray (disabled)
created  dashboard Signal Dynamics · Security telemetry overview
skip     dashboard 'Signal Dynamics · Detection & alert activity': <catalog>.__lakewatch.signals not found yet (it appears with the first alerts; start_replay adds this dashboard)
running  ingestion for sd_okta (already in progress)

Setup done. Ingestion of the week of logs is running: about 10 minutes. Then run action = status.
ℹ️

다시 실행해도 안전합니다
모든 action은 다시 실행해도 됩니다. setup은 이미 있는 리소스를 건너뜁니다. 여러 사람이 동시에 실행하다가 API 속도 제한(rate limit) 오류가 나면 Run all을 다시 누르세요.

완료 기준: 출력 마지막에 "Setup done. Ingestion of the week of logs is running: about 10 minutes."가 나옵니다.

E. status로 확인

setup 약 10분 뒤 action을 status로 바꾸고 Run all을 누릅니다. 몇 초면 끝납니다.

status는 이벤트 테이블 5개의 행 수와 시간 범위, 규칙 수와 켜진 규칙 수, 데이터소스별 수집 Job, 마지막 재생 기록, Genie 스페이스와 대시보드 링크, 실습 Alert 수를 출력하고 마지막 줄에 상태를 알려 줍니다.

마지막 줄뜻할 일
READY: run start_replay.다섯 테이블에 행이 있고 규칙 17개가 꺼진 채 있음6단계로 진행
NOT READY: …수집이 아직 끝나지 않았거나 규칙이 모자람잠시 뒤 status를 다시 실행. 규칙이 모자라면 setup을 다시 실행
RUNNING: rules are on.규칙이 켜져 있음실습 중이 아니면 pause 실행

검증 환경에서 수집이 끝난 뒤 이벤트 테이블의 행 수는 아래와 같았습니다. 합성 데이터라 실행마다 조금씩 다를 수 있습니다.

테이블행 수
sd_cloudtrail_events40,928
sd_okta_events726
sd_agent_egress_events191
sd_agent_tool_events181
sd_ai_gateway_events159

완료 기준: status의 마지막 줄이 READY입니다.

비용

  • 데이터소스는 일정이 10일 간격이라 평소에는 돌지 않습니다.
  • 탐지 규칙은 켜진 동안 1시간마다 SQL 웨어하우스에서 실행됩니다.
  • 사고를 재생하면 3시간 뒤(autopause_hours) 자동으로 pause가 실행되도록 Job이 예약됩니다.
