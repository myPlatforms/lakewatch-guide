10. 정리와 재실행

10단계 - 정리와 재실행

실습을 마치면 pause로 규칙과 수집을 멈춥니다. 데이터와 Alert는 남으므로 나중에 다시 시연할 수 있습니다. 더 쓰지 않을 때는 teardown으로 실습 리소스를 지웁니다. 문제 해결 표와 사고 단계 참조 표도 이 페이지에 있습니다.

ℹ️

확인 범위
A의 pause, B의 대시보드와 Overview 화면, 문제 해결 표의 일부 항목은 2026-11-23 실습에서 검증 워크스페이스로 확인했습니다. C의 teardown은 실행하지 않아(검증 환경을 남겨 두기 위해) 실습 노트북 코드 기준입니다.

A. 일시 중지

노트북에서 action을 pause로 바꾸고 Run all을 누릅니다. 검증 환경에서는 일회성 실행으로 약 1분 걸렸습니다.

  • 실습 규칙(sd_로 시작)이 모두 꺼집니다. 9단계에서 직접 만든 규칙도 이름이 sd_로 시작하면 함께 꺼집니다.
  • 데이터소스의 수집 일정을 10일 간격으로 둡니다. 데이터소스는 일시 중지할 수 없어(Lakewatch가 멈춘 Job을 되돌립니다) 일정을 길게 늘리는 방식을 씁니다. 검증 환경에서는 pause 전에도 다섯 개 모두 이미 10일 간격이었습니다.
  • 자동 일시 중지 Job의 예약이 멈춥니다.
  • 데이터와 Alert는 그대로 남습니다.

pause는 실행 전 상태, 한 일, 실행 후 상태를 차례로 출력합니다. 검증 환경의 출력 일부입니다.

Detection rules: 18 (18 enabled)
WARNING: 18 rule(s) enabled; they run on schedule and cost compute. Use mode=pause or teardown.

== PAUSE
done: disable rule sd_okta_password_spray
done: pause ingestion for datasource sd_okta (job …)

== After
Detection rules: 18 (0 enabled)
Datasources: 5 (0 ingesting, 5 paused)
No problems found.
Auto-pause job … paused.

사고를 재생한 뒤 3시간이 지나면 같은 pause가 자동으로 실행됩니다. 그래도 실습을 마치면 직접 실행하세요. 규칙이 켜져 있는 동안에는 1시간마다 다시 실행되어 Alert가 더 생길 수 있습니다. 검증 환경에서는 재생 뒤 1시간에서 1시간 15분 사이의 정기 실행에서 Alert가 2건 더 생겼습니다(대량 다운로드 규칙 1건, Extend lookback을 2h로 둔 직접 만든 규칙 1건).

완료 기준: pause 출력의 After 부분에서 규칙 줄이 "0 enabled"이고 "No problems found."가 나옵니다.

B. 다시 시연하기 (M8)

같은 환경으로 다음 시연을 준비하는 순서입니다.

시점할 일
전날Lakewatch가 켜진 워크스페이스에 노트북을 가져오고 setup → status가 READY인지 확인 (처음부터 끝까지 약 15분)
5분 전start_replay. 새 피해자로 사고가 재생되고 약 3–5분 뒤 Alert가 도착합니다. 시연의 첫 장면으로 직접 실행해도 됩니다
시연 중6–9단계의 미션. 새 피해자 이름으로 Alert를 걸러 봅니다
끝난 뒤pause

실습이 만든 AI/BI 대시보드 세 개(탐지, 신원 위험, 원격 측정)도 살펴보세요. 두 개는 setup이, 탐지 대시보드는 start_replay가 만들고, 링크는 start_replay와 status가 출력합니다. 아래는 9단계까지 마친 뒤의 탐지 대시보드입니다. Signal 22건과 Alert 22건(재생 21건과 직접 만든 규칙 1건), 발동한 규칙 18개가 보입니다.

같은 시점의 Lakewatch Overview입니다. 3단계에서 비어 있던 화면에 수집량, Signal 수, 켜진 규칙 수, 열린 Alert가 채워져 있습니다.

ℹ️

자주 묻는 질문

  • 실제 데이터입니까? 합성 데이터입니다. 실제 CloudTrail·Okta 스키마를 본떴고 IP는 문서용 대역입니다.
  • 탐지까지 얼마나 걸립니까? 규칙은 일정에 따라 실행되므로 실시간 탐지는 아닙니다. 이 실습은 1시간 창이고, 재생할 때 수집을 바로 실행하고 규칙을 켜는 즉시 실행하므로 Alert가 몇 분 안에 도착합니다. 일정을 촘촘히 하면 지연이 줄고 비용이 늡니다.
  • 비용은 얼마입니까? Databricks 소비량 기준입니다(규칙은 서버리스 SQL, 수집은 Job). 이 실습의 수치는 실제 환경의 비용과 다르므로, 예상 비용은 담당 어카운트팀에 문의하세요.

C. 삭제

실습 환경이 더 필요 없으면 지웁니다.

  1. 노트북에서 action을 teardown으로 바꿉니다.
  2. confirm 위젯에 스키마 이름(signal_dynamics_lab)을 입력합니다.
  3. Run all을 누릅니다. 몇 분 걸립니다.

teardown이 지우는 것은 실습 규칙과 그 Alert, 데이터소스, 사용자 지정 파서, 이벤트 테이블, 볼륨의 원시 파일, sd_threat_intel_ip·sd_lab_replays 테이블, 자동 일시 중지 Job, Genie 스페이스, 대시보드입니다. 스키마 <catalog>.signal_dynamics_lab과 빈 볼륨은 남으므로 필요하면 Catalog Explorer에서 지웁니다.

⚠️

규칙을 지우면 Alert도 지워집니다
Lakewatch는 규칙을 삭제할 때 그 규칙의 Alert를 함께 삭제합니다. Alert를 남겨 두려면 teardown 대신 pause를 쓰세요.

Lakewatch 환경 자체(카탈로그)는 teardown이 지우지 않습니다. 환경을 없애는 방법은 3단계 E의 안내를 보세요.

문제 해결

증상조치
status가 NOT READYsetup 뒤 수집에 약 10분이 걸립니다. 잠시 뒤 status를 다시 실행합니다
노트북이 "Lakewatch isn't enabled"라고 함2단계와 3단계를 마치고 Lakewatch를 한 번 연 뒤 다시 실행합니다
노트북이 "several Lakewatch environments"라고 함워크스페이스에 환경이 여러 개입니다. catalog 위젯에 쓸 카탈로그 이름을 입력합니다
setup이 "schema 'signal_dynamics_lab' is not a registered folder"로 실패스키마를 폴더로 등록한 뒤 setup을 다시 실행합니다 (5단계 C)
"Lakewatch didn't answer for catalog …"앱 전환기에 Lakewatch가 보이는지, 그 카탈로그에 Lakewatch 권한(CREATE_DATASOURCE, CREATE_RULE)이 있는지 확인합니다
실습 리소스가 Lakewatch 화면에 안 보임Environment를 노트북이 출력한 카탈로그로 바꿉니다. 리소스는 만들어진 카탈로그 아래에서만 보입니다
카탈로그 이름이 lakewatch가 아님같은 메타스토어에서 그 이름이 이미 쓰이고 있으면 다른 이름이 됩니다. 이 가이드의 <catalog> 자리에 노트북이 출력한 이름을 씁니다
Query에서 table not found<catalog>.signal_dynamics_lab.<table> 전체 이름을 씁니다
start_replay 5분 뒤에도 Alert가 없음status를 실행하고 Lakewatch의 System errors를 확인합니다
Datasources에 이벤트 수가 안 보임선택된 SQL 웨어하우스가 서버리스인지 확인합니다 (1단계 B)
Genie가 느리거나 멈춤진행 중인 단계의 Stop으로 멈추고 한 번 다시 시도합니다. 답이 "This response was interrupted before it finished."로 끊기면 Resend를 누릅니다. 안 되면 Query에서 직접 조회하거나 정답 SQL을 씁니다 (9단계 B)
직접 만든 규칙을 저장했는데 Alert가 없음규칙의 첫 실행 시간 창이 재생 이벤트보다 뒤에서 시작했을 수 있습니다. Edit rule에서 Extend lookback에 2h를 넣고 저장하거나 start_replay를 다시 실행합니다 (9단계 B)
직접 만든 규칙의 Alert가 SD: 검색에 안 나옴규칙의 Signal summary가 SD:로 시작하는지 확인합니다
한 시간 안에 start_replay를 두 번 실행함첫 재생의 Alert 몇 건이 다시 올라옵니다. 정상입니다
API 속도 제한(rate limit) 오류Run all을 다시 누릅니다. 모든 action은 다시 실행해도 안전합니다

데이터소스나 탐지 규칙이 실패하면 Lakewatch가 시스템 오류를 열고 반복되는 실패를 묶습니다. 자세한 내용은 시스템 오류 (opens in a new tab)를 참조하세요.
