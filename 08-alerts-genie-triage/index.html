8. Alert 처리와 Genie 분류

8단계 - Alert 처리와 Genie 분류

사고 1의 Alert 대기열에서 사고의 시작점을 찾아 맡고, Genie와 함께 조사해 근거가 있는 판정을 남깁니다. 미션 M4와 M5입니다.

ℹ️

확인 범위
이 페이지의 절차는 2026-11-23에 검증 워크스페이스에서 끝까지 수행했고, Genie 패널도 동작했습니다. Genie의 답은 실행할 때마다 달라지므로, 아래에 옮긴 Genie의 계획과 답은 한 번의 실행 예시입니다.

학습 목표

  1. Alert 대기열을 검색·정렬해 사고의 첫 Alert를 찾는다
  2. Alert의 Signal과 이를 만든 탐지 규칙을 확인한다
  3. Genie에게 읽기 전용 조사를 시키고 계획과 SQL, 근거를 검토한다
  4. Alert에 근거를 남기고 분류와 상태를 기록한다

A. Alert 대기열 처리 (M4)

재생 한 번으로 Alert가 21건 생깁니다. 사고 1에서 17건(root 로그인 미끼 포함), 사고 2에서 4건입니다.

  1. Alerts를 엽니다. 목록의 기본 필터는 State: Active, Severity: Low+, All time입니다. 검색창에 SD:를 입력합니다.

  2. 사고 흐름에서 가장 먼저 일어난 Alert를 찾습니다. Created와 Updated 열 머리글을 눌러 정렬할 수 있지만, 이 두 열은 이벤트 시각이 아닙니다(아래 "읽는 법").

  3. 심각도 Critical인 "Spray … succeeded" Alert를 엽니다. Overview 탭에는 설명과 댓글이, 오른쪽에는 담당자, 심각도, 분류, 규칙 링크, 첫 이벤트·마지막 이벤트·생성·갱신 시각이 있습니다.

  4. Signals 탭을 열고 Signal을 누릅니다. Signal details에 이 Signal의 행위자와 자원(공격자 IP, 실패한 사용자 수), 이벤트 시각(Event time)과 탐지 시각(Detected time), Signal을 만든 규칙과 규칙 버전이 보입니다.

  5. Overview 탭으로 돌아와 Assignee를 열고 Assign to me를 선택합니다.

  6. 제목 오른쪽의 상태 메뉴(Open)를 열어 In progress로 바꿉니다. 상태는 Open, In progress, Mitigated, Resolved, Duplicate 다섯 가지입니다.

읽는 법

  • 탐지 규칙은 조건에 맞는 이벤트를 찾으면 Signal을 만들고, Lakewatch가 관련 Signal을 Alert로 묶습니다. Alert를 열면 Signal과 그 Signal을 만든 규칙을 볼 수 있습니다.
  • 생성 시각이 아니라 이벤트 시각 순서로 읽으세요. 생성 시각은 규칙이 실행되어 Alert를 쓴 시각입니다. 검증 환경에서 가장 먼저 만들어진 Alert는 대량 다운로드(23:09:16)였고, 비밀번호 스프레이 Alert는 그보다 뒤(23:09:23)에 만들어졌습니다. 하지만 이벤트 시각은 스프레이가 22:57:55로, 대량 다운로드보다 앞섭니다. 생성 순서대로 위에서부터 처리하면 이야기의 중간부터 보게 됩니다.
  • 목록에는 이벤트 시각 열이 없습니다. Alert를 열어 오른쪽의 First event를 보거나 Signals 탭의 Event time을 봅니다.
  • 제목에 사용자, IP, 계정이 들어 있으므로(규칙의 Signal 요약) 검색창으로 관련 Alert를 찾아 들어갈 수 있습니다.

확인 질문: 사고 흐름에서 어느 Alert가 가장 먼저입니까?

정답

이벤트 시각 기준으로 비밀번호 스프레이(sd_okta_password_spray) Alert가 가장 먼저입니다. 검증 환경에서 이 Alert의 첫 이벤트는 22:57:55였고, 스프레이 후 성공(sd_okta_spray_then_success)과 새 국가 로그인(sd_okta_signin_new_country)이 22:58:04로 그다음이었습니다.

완료 기준: "Spray … succeeded" Alert의 담당자가 본인이고 상태가 In progress입니다.

Alert의 상태, 분류, 내보내기는 Alert (opens in a new tab)를 참조하세요.

B. Genie로 분류하기 (M5)

  1. A에서 맡은 Alert를 연 채로, 화면 오른쪽 위의 Genie 아이콘을 눌러 Genie 패널을 엽니다. Alert 오른쪽의 Triage with Genie 버튼이 아닙니다. 패널 아래쪽에 "Summarize this alert", "Triage this alert" 같은 추천 질문이 보입니다.

  2. 아래처럼 읽기 전용으로 조사를 시킵니다.

    Investigate this alert read-only. Don't change the alert yet. Show the plan, the SQL and the evidence.

  3. Genie가 내놓는 계획(Plan)을 먼저 확인합니다. 검증 환경에서는 다섯 단계였습니다. 규칙·Signal·이력 확인, 가설 세우기, Okta 이벤트 조회, CloudTrail로 범위 넓히기, 근거를 갖춘 판정(변경 없음) 순서입니다.

  4. 답을 읽습니다. 검증 환경에서는 약 3분 뒤 답이 나왔고, 계획과 가설, 실행한 SQL(조회 7건), 근거 표, 주의할 점과 남은 질문으로 구성돼 있었습니다. 조사가 아래 범위를 다뤘는지 확인하고, 빠진 것이 있으면 이어서 묻습니다.

    순서확인할 것데이터
    1공격자 IP의 로그인 기록Okta
    2피해자의 AWS 세션CloudTrail
    3새 IAM 사용자와 액세스 키CloudTrail
    4대량 다운로드CloudTrail
    5버킷 공개 설정CloudTrail

    다음 질문이 도움이 됩니다.

    What did this user and this IP do next, in Okta and in AWS?
    Did the attacker create any persistence? Follow any new identities.

  5. 근거를 댓글로 남깁니다. 직접 써도 되고, 답 아래의 추천 질문 Add this as a triage comment를 눌러 Genie에게 맡겨도 됩니다. 검증 환경에서 Genie는 요약, 판정, 근거 표, 탐지 품질 평가, 다음 조치로 구성된 댓글을 Alert에 추가했습니다. 분류와 상태는 바꾸지 않았습니다.

  6. Classification을 True positive(진양성)로, 상태를 Mitigated로 바꿉니다. 분류는 Unspecified, False positive, Benign positive, True positive 네 가지입니다.

읽는 법

  • Triage with Genie는 Genie가 Alert를 스스로 조사해 판정까지 제안하는 기능이고, 이 미션에서는 Genie 패널에서 대화하며 단계마다 확인하는 방식을 씁니다. 두 방식의 차이는 Genie로 Alert 분류하기 (opens in a new tab)를 참조하세요.
  • 조사가 놓치기 쉬운 지점이 있습니다. 공격자는 중간에 신원과 IP를 바꿉니다. 처음의 스프레이 IP는 조용해지고, 새로 만든 IAM 사용자의 액세스 키가 다른 IP에서 쓰입니다. 원래 IP만 따라가면 로깅 중지, 대량 다운로드, 버킷 공개를 놓칩니다. 그래서 "새로 만들어진 신원을 따라가라"는 질문이 필요합니다. 검증 환경의 실행에서는 Genie가 첫 답에서 백도어 사용자와 두 번째 IP까지 따라갔지만, 매번 그렇다고 볼 수는 없습니다.
  • Genie는 같은 SQL을 두 번 쓰지 않습니다. 결과를 받아들이기 전에 SQL과 근거를 직접 읽으세요. 검증 환경의 답에는 Genie가 스스로 적은 한계도 있었습니다. 조회 한 건이 100행 제한에 걸려 집계로 다시 실행했고, 새 버킷 정책의 내용은 읽지 않았다는 점입니다.
  • "읽기 전용"은 질문으로 정한 범위입니다. 추천 질문을 누르면 Genie가 댓글을 쓰거나 분류를 바꾸므로, 누르기 전에 무엇을 바꾸는 질문인지 확인하세요.
  • root 콘솔 로그인 Alert(MFA 사용, 사무실 IP)는 위양성이 아니라 무해 양성(benign positive)입니다. 규칙은 맞게 발동했지만 활동이 정상입니다. 시간이 남으면 이 Alert를 Benign positive로 닫는 연습을 합니다.
ℹ️

Genie가 멈추거나 느릴 때
진행 중인 단계 옆의 Stop으로 멈추고 한 번 다시 시도합니다. 답이 "This response was interrupted before it finished."로 끊기면 옆의 Resend를 누릅니다. 그래도 안 되면 위 표의 순서대로 Query에서 직접 조회합니다. 검증 환경에서는 이 미션은 한 번에 끝났고, 9단계의 규칙 만들기에서 멈춤과 끊김이 있었습니다.

확인 질문: 공격자가 만든 백도어 IAM 사용자의 이름은 무엇입니까? (Alert가 가리키는 테이블 밖의 다른 테이블도 봐야 할 수 있습니다)

정답

svc-backup-sync입니다(검증 환경의 Alert 제목과 Genie의 답에서 확인). 이 사용자에게 AdministratorAccess와 액세스 키가 붙고, 이 키가 다른 IP에서 StopLogging, GuardDuty 삭제 시도, 1,400건의 GetObject, 버킷 공개에 쓰입니다.

완료 기준: Alert에 근거 댓글이 있고, 분류가 True positive, 상태가 Mitigated입니다.
