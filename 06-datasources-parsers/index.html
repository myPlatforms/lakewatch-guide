6. 사고 재생과 데이터소스·파서

6단계 - 사고 재생과 데이터소스·파서

start_replay로 두 사고를 재생합니다. Alert가 도착하기까지 몇 분 걸리므로, 그동안 로그 한 줄이 원시 파일에서 파싱된 행이 되기까지의 경로(데이터소스 → 파서 → 테이블)를 따라갑니다. 미션 M0과 M1입니다.

ℹ️

확인 범위
이 페이지의 사고 재생(A)과 데이터소스·파서 화면(B–D)은 2026-11-23에 검증 워크스페이스에서 실행해 확인했습니다. 피해자와 IP는 재생할 때마다 달라지므로 아래 예시 값은 본인 출력과 다릅니다.

학습 목표

  1. 사고를 재생하고, 재생이 출력하는 피해자·공격자 정보를 기록한다
  2. 데이터소스의 원본 위치, 일정, 컴퓨팅 모드를 찾는다
  3. 파서가 이벤트 시각을 어느 필드에서 가져오는지 찾는다
  4. 원시 테이블과 파싱된 테이블을 비교한다

미션 전체에서 기억할 것

항목내용
환경상단의 Environment, workspace and compute에서 Environment가 본인 카탈로그인지 확인합니다. 리소스는 만들어진 카탈로그 아래에서만 보입니다
Alert 찾기실습 Alert의 제목은 모두 SD:로 시작합니다. Alerts에서 SD:로 검색합니다
테이블 이름Query 페이지에는 기본 카탈로그가 없습니다. <catalog>.signal_dynamics_lab.<table>처럼 전체 이름을 씁니다
시각로그의 time 컬럼과 노트북 출력은 UTC입니다. 검증 환경의 Alerts 목록은 열 이름에 Created(GMT+9)처럼 브라우저 시간대를 표시했습니다. 시각을 비교할 때 어느 기준인지 확인하세요

A. 사고 재생 시작 (M0)

  1. signal_dynamics_lab 노트북에서 action을 start_replay로 바꾸고 Run all을 누릅니다.

  2. 출력된 값을 적어 둡니다.

    사고출력되는 값
    사고 1피해자(victim), 공격자 IP와 국가, 유출 IP(exfil)
    사고 2에이전트 사용자, 샌드박스 이름, 유출 도메인

  3. 노트북은 그대로 두고 B로 넘어갑니다. Alert는 약 3–5분 뒤에 도착합니다.

검증 환경에서 출력은 아래와 같았습니다(일부).

Incident 1 (identity -> cloud): victim frankie.nguyen@signaldynamics.example, attacker 203.0.113.116 (Germany), exfil 198.51.100.206.
Incident 2 (AI agent): agent session for kai.okafor@signaldynamics.example in sandbox sd-eng-assistant-sbx-07, exfil to doc-preview-f15c.example.

수집 Job 다섯 개는 95초 만에 끝났고, 규칙을 켠 지 약 2분 뒤에 Alert 21건이 모두 도착했습니다.

start_replay가 하는 일은 다음 순서입니다(노트북 코드와 위 출력 기준).

  1. 실습 규칙을 모두 끕니다.
  2. 지금 시각에 끝나는 두 사고의 로그를 새로 만들어 볼륨에 씁니다. 피해자와 IP는 매번 다릅니다.
  3. 데이터소스 다섯 개의 수집 Job을 바로 실행하고 끝날 때까지 기다립니다(약 2–4분).
  4. 규칙을 켭니다. 규칙은 켜는 즉시 한 번 실행됩니다.
  5. 자동 일시 중지 Job을 3시간 뒤로 예약하고, 위협 헌팅용 Genie 스페이스를 만듭니다.
  6. Alert가 약 21건 도착할 때까지(최대 8분) 건수를 출력합니다.
  7. 대시보드 두 개를 갱신하고 세 번째 대시보드(Detection & alert activity)를 만듭니다.
ℹ️

재생은 한 시간에 한 번
한 시간 안에 두 번 재생하면 첫 재생의 Alert 몇 건이 다시 올라옵니다. 정상 동작입니다.

확인 질문: 피해자는 누구이고, 공격자는 어느 나라에서 접속했고, 유출 도메인은 무엇입니까?

B. 데이터소스 살펴보기 (M1)

  1. Lakewatch에서 Datasources를 엽니다. 실습 데이터소스 다섯 개가 보입니다. 유형은 모두 Unity Catalog volume이고 Schedule은 Every 1w3d(10일)입니다.

  2. sd_okta를 선택합니다. 상세 화면은 Overview, Parsers, Configuration, Run history, System errors 탭으로 나뉩니다.

  3. Overview에서 다음을 찾습니다.

    찾을 것화면의 위치값
    원본Source and access > Location, File format/Volumes/<catalog>/signal_dynamics_lab/sd_raw_logs/okta/, JSONL
    원시 테이블Raw landing table<catalog>.signal_dynamics_lab.sd_okta_raw
    일정Processing > ScheduleEvery 1w3d. 평소에는 돌지 않고, 재생할 때 노트북이 수집을 직접 실행합니다
    컴퓨팅 모드Processing > Compute modePerformance optimized
    마지막 실행Run status > Latest runSucceeded

  4. sd_cloudtrail을 열어 비교합니다. 형식은 JSON이고, 사용자 지정 파서 없이 내장 AWS CloudTrail 파서(aws_cloudtrail)를 씁니다.

ℹ️

수집 직후에는 이벤트 수가 0으로 보일 수 있습니다
검증 환경에서 첫 수집이 성공한 직후, 목록의 7-day events와 상세의 Ingestion activity, Parsers 탭의 행 수는 모두 0이었습니다. 같은 시점에 파싱된 테이블에는 행이 들어와 있었습니다. 데이터가 들어왔는지는 테이블을 직접 조회하거나 노트북의 status로 확인하세요.

C. 파서 읽기

  1. sd_okta 데이터소스의 Parsers 탭에서 파서 sd_okta_system_log를 엽니다(또는 왼쪽 메뉴의 Parsers에서 찾습니다). 파서 화면은 Schema, YAML, Datasources 탭으로 나뉩니다.

  2. Schema 탭 맨 위의 Event time을 봅니다. "Uses the first source that can be parsed as a timestamp, in order. Falls back to ingestion time if none can be parsed."라는 설명 아래에 시각을 가져오는 필드가 나옵니다. 그 아래에는 최상위 필드 17개가 유형·설명과 함께 나열됩니다.

  3. YAML 탭에서 같은 내용의 time: 블록을 찾습니다. 이 블록이 탐지 규칙이 필터링하는 time 컬럼을 만듭니다.

    time:
  coalesce:
  - path: published
    time_formats:
    - '#rfc3339'

  4. scan_for_observables를 하나 찾습니다. 예를 들어 client 필드는 ipaddress 값을 ip Observable(관측 대상)로 뽑습니다.

    - name: client
  type: VARIANT
  comment: The client that requested an action
  scan_for_observables:
    ip:
      equals:
      - ipaddress

파서는 로그 소스의 출력 컬럼을 정의하고, Lakewatch가 관리하는 lw_id, lw_meta, lw_observables 컬럼이 붙은 파싱된 테이블을 씁니다. Observable은 서로 다른 로그 소스를 IP나 사용자 같은 공통 값으로 넘나들 때 씁니다. 문법은 파서 참조 (opens in a new tab)에 있습니다.

D. 원시 테이블과 파싱된 테이블 비교

  1. 워크스페이스의 Catalog에서 <catalog>.signal_dynamics_lab을 엽니다.
  2. sd_okta_raw와 sd_okta_events를 차례로 열어 컬럼과 샘플 데이터를 비교합니다.
테이블구조
sd_okta_raw원본 레코드가 통째로 든 VARIANT 컬럼 data 하나(와 _metadata)
sd_okta_events파서가 정의한 컬럼들과 UTC time, lw_observables

확인 질문: Okta 파서는 이벤트 시각을 원본의 어느 필드에서 가져옵니까?

정답

published 필드입니다. RFC 3339 형식의 시각으로 읽습니다. 파서의 Event time에 published · #rfc3339로 표시됩니다(검증 환경에서 확인).

완료 기준: 로그 한 줄이 볼륨의 파일 → 원시 테이블 → 파싱된 테이블로 이어지는 경로를 설명할 수 있습니다.
