7. 탐지 규칙 읽기와 검증

7단계 - 탐지 규칙 읽기와 검증

탐지 규칙 하나를 열어 무엇이 규칙을 발동시키는지 읽고, 같은 SQL을 Query에서 기간과 임계값을 바꿔 가며 실행해 임계값이 왜 그 값인지 확인합니다. 미션 M2와 M3입니다.

ℹ️

확인 범위
A의 탐지 규칙 화면과 B의 쿼리 결과는 2026-11-23에 검증 워크스페이스에서 실행해 확인했습니다(사고 재생 1회 기준).

학습 목표

  1. 탐지 규칙의 SQL을 읽고 발동 조건을 한 문장으로 말한다
  2. 규칙의 MITRE ATT&CK 매핑, 심각도, Alert 제목 템플릿, 일정을 찾는다
  3. 규칙 SQL을 과거 데이터에 실행해 임계값의 절충을 확인한다

A. 탐지 규칙 읽기 (M2)

  1. Detection rules를 엽니다. 실습 규칙 17개가 보입니다. 6단계에서 사고를 재생했다면 상태가 Active이고, 아래 캡처처럼 재생 전이거나 pause 뒤라면 Inactive입니다.

  2. sd_okta_spray_then_success를 엽니다. 상세 화면은 Overview, Configuration, Run history, Alerts, System errors 탭으로 나뉩니다. Configuration 탭은 규칙 전체를 YAML로 보여 줍니다.

  3. Input configuration의 Detection SQL을 읽습니다. 이 규칙은 SQL 파이프 구문으로 쓰여 있습니다.

    FROM sd_okta_events
|> WHERE IN_TIMERANGE(time) AND eventType = 'user.session.start'
|> AGGREGATE
     count(DISTINCT CASE WHEN outcome:result::string = 'FAILURE' THEN actor:alternateId::string END) AS users_failed,
     array_compact(collect_set(CASE WHEN outcome:result::string = 'SUCCESS' THEN actor:alternateId::string END)) AS compromised_users,
     max(time) AS time
   GROUP BY client:ipAddress::string AS source_ip
|> WHERE users_failed >= 5 AND size(compromised_users) > 0

  4. 다음 항목을 찾습니다.

    항목화면의 위치이 규칙의 값
    상태Rule details > StateInactive
    심각도·신뢰도·범주Rule detailsCritical · High · Behavioral
    일정Execution > ScheduleEvery 1h
    실행 IDExecution > Run as규칙을 만든 사용자
    Signal 요약 (Alert 제목이 됨)Signal output > Signal summarySD: Spray from {source_ip} succeeded for {compromised_users} after failing {users_failed} users
    런북Runbook침해된 사용자 조치 절차
    MITRE ATT&CKMITRE ATT&CK아래 확인 질문

  5. Edit rule을 눌러 편집 화면을 엽니다. 편집 화면은 Detection input, Signals, MITRE ATT&CK, Metadata, Execution 다섯 구역입니다. 규칙을 켜고 끄는 설정은 Execution의 Status에, Alert 생성 설정은 Signals의 Generate alerts에 있습니다. 값은 바꾸지 말고 Cancel로 나옵니다.

읽는 법

  • IN_TIMERANGE(time)은 스케줄러가 실행할 때마다 규칙의 시간 창으로 채워 줍니다. 저장된 규칙은 시간 조건을 직접 쓰지 않고 이 함수를 씁니다.
  • 조건을 한 문장으로 옮기면 "시간 창 안에서 같은 IP가 5명 이상의 사용자에 대해 로그인에 실패했고, 그 IP에서 성공한 로그인이 하나 이상 있다"입니다.
  • 이 SQL은 순서를 강제하지 않습니다. 실패와 성공이 같은 시간 창에 있다는 것만 확인하고, 성공이 실패 뒤에 왔는지는 확인하지 않습니다. 제목은 "after"라고 말하지만 조건이 증명하는 것은 그보다 좁습니다. 규칙의 조건이 증명하는 것과 제목이 주장하는 것을 구분해서 읽으세요.
  • Detection SQL 옆의 Open in Query는 이 SQL을 쿼리 페이지로 가져갑니다. 아래 B처럼 과거 데이터에 시험할 때 씁니다.
  • Extend lookback은 늦게 도착하는 데이터를 위해 실행 시간 창의 시작을 앞으로 늘리는 설정입니다. 비워 두면 기본 15분이 적용되고, SQL이 IN_TIMERANGE를 쓸 때만 효과가 있습니다.
  • Signal 요약의 {source_ip} 같은 자리표시자는 결과 컬럼 값으로 채워집니다. 그래서 Alert 제목에 사용자와 IP가 들어가고, 검색창으로 찾아 들어갈 수 있습니다.

확인 질문: 이 규칙은 어떤 MITRE ATT&CK 기법 두 가지에 매핑되어 있습니까?

정답

T1110.003 Password Spraying(Credential Access)과 T1078 Valid Accounts(Initial Access)입니다(규칙 화면의 MITRE ATT&CK에서 확인).

완료 기준: 규칙의 발동 조건을 한 문장으로 말할 수 있습니다.

B. 과거 데이터로 규칙 시험하기 (M3)

규칙을 켜기 전에 SQL을 과거 데이터에 돌려 보면 임계값이 무엇을 잡고 무엇을 놓치는지 알 수 있습니다. 여기서는 sd_okta_password_spray 규칙의 SQL을 씁니다.

  1. Query에서 New SQL query를 누르고 아래 SQL을 붙여 넣습니다. <catalog>를 본인 카탈로그로 바꿉니다.

    SELECT client:ipAddress::string AS source_ip,
       count(DISTINCT actor:alternateId::string) AS distinct_users,
       count(*) AS failures,
       max(time) AS last_failure
FROM <catalog>.signal_dynamics_lab.sd_okta_events
WHERE time >= current_timestamp() - INTERVAL 3 HOURS
  AND eventType = 'user.session.start'
  AND outcome:result::string = 'FAILURE'
GROUP BY 1
HAVING count(DISTINCT actor:alternateId::string) >= 10
ORDER BY last_failure DESC

  2. 실행합니다. 6단계에서 적어 둔 공격자 IP가 나와야 합니다.

  3. 3 HOURS를 7 DAYS로 바꿔 다시 실행합니다. 무엇이 더 나옵니까?

  4. >= 10을 >= 3으로 낮춰 다시 실행합니다. 새로 나온 IP는 공격입니까?

실행검증 환경에서 나온 결과 (재생 1회)
최근 3시간, 10명 이상IP 1개. 방금 재생한 공격자(사용자 27명, 실패 27회)
최근 7일, 10명 이상IP 2개. 공격자와 203.0.113.66. 뒤의 것은 setup이 일주일치 로그에 심어 둔 하루 이상 지난 공격입니다
최근 7일, 3명 이상IP 4개. 위의 둘과 192.0.2.10, 192.0.2.20(각각 사용자 4명)

Query 페이지 위쪽에는 시간 범위 선택기가 있고 기본값은 최근 24시간으로 표시됩니다. 검증 환경에서는 SQL에 직접 쓴 시간 조건(7 DAYS)대로 일주일치 결과가 나왔습니다.

192.0.2.10과 192.0.2.20은 Signal Dynamics 사무실의 출구 IP입니다. 사무실에서는 여러 사용자가 평소에도 비밀번호를 틀리므로, 임계값이 낮으면 이런 정상 활동이 위양성으로 잡힙니다. 임계값은 추측으로 정하는 값이 아니라 과거 데이터로 시험해 정하는 절충입니다.

ℹ️

Beta의 제한
규칙을 켜면 자기 시간 창을 대상으로 한 번 실행될 뿐, 그보다 오래된 기간으로 소급 실행(backfill)되지는 않습니다. 검증 환경에서 이 첫 실행의 시간 창은 규칙마다 달라, 짧게는 17분 전부터 길게는 1시간 14분 전부터였습니다. 규칙을 켜기 전에 Query 페이지나 노트북에서 SQL을 과거 데이터에 돌려 확인하세요.

확인 질문: 임계값 3, 최근 7일로 실행하면 원본 IP가 몇 개 나옵니까?

정답

재생을 한 번 했다면 4개입니다(검증 환경에서 확인). 재생을 여러 번 했다면 재생마다 공격자 IP가 달라 더 많이 나올 수 있습니다.

완료 기준: 규칙을 두 기간에 대해 실행했고, 임계값을 낮추면 위양성이 늘어나는 것을 확인했습니다.

쿼리 페이지의 기능(시간 범위, 타임라인, 결과 세분화)은 Lakewatch에서 데이터 쿼리 (opens in a new tab)를 참조하세요.
